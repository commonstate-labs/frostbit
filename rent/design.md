# 惰性收租设计

日期：2026-09-22。状态：本地实现完成，待首次发布。本方案直接替换尚未发布的第一版租金行为，不增加协议版本或升级高度，也不包含部署或线上恢复。

## 目标与当前边界

账户不活动时不逐块读写；查询能看见已经产生的租金；发生资金变动时不能花掉欠租对应的资金；到期账户按索引分页处理，但当前高度已到期的工作必须在同一块全部完成。

实现由 `rent/accrual.go` 统一计算投影与结算，`rent/scheduler.go` 按到期索引建立当块确定性工作集，`vm/rent_hooks.go` 负责 StateView 适配、资金来源清理和块末 touched owners。主动交易在手续费和业务执行前结租，因此转出前已经产生的租金不会被绕过。

保留当前基础规则：

- 仅管理本链用户地址；协议账户不进入租金生命周期。
- 每块租金为 100 最小单位 FB，FB 精度为 8。
- 10 FB 或任一白名单外置资产独立达到固定门槛免租，门槛不按市场价格动态估算，也不跨资产相加。`ETH.USDT` 当前门槛为 10 USDT，所以 1 ETH.USDT 不免租。
- 复用 `rent_state_`、`rent_expiry_`、资产 claim 聚合、既有资金归集账户和 VM cleaner。

第一版采用以下规则：**名义资产用于免租判定，可用 FB 用于支付租金和计算资金可维持的期限。** 冻结余额、仓位保证金、挑战质押虽然计入名义资产，不能直接当作可花 FB。相较旧的“所有名义 FB 都支撑租期”，小额且全部锁仓的账户会更早需要补租，Explorer 与钱包会分别展示账面、待结租和可花余额。

## 统一计算模型

将纯计算投影与真实结算分开：

- `ProjectRent(owner, height, view)`：只读，返回累计应付租金、可付金额、欠租、有效可用余额及状态。
- `SettleRent(owner, height, view)`：复用同一计算结果，在当前 StateView 真实扣款并给租金 fund 入账。
- `RefreshRentEligibility(owner, height, view)`：资金变动后重新判定免租和下次到期高度，不免除旧欠租。

这些接口已经落在 `rent/` 中。`GetBalance` 不会隐式扣租、撮合或清户；只读调用不改变共识状态。

`rent_state_` 保存持久计提游标 `last_accrued_height`、兼容字段 `last_settled_height`、已计提未支付的 `unpaid_fb`、收费状态和经济到期高度 `expire_height`。`last_settled_height` 表示最近一次租金状态处理/落盘高度，处理金额可能为零，不能把它解释成最近一次正额扣款高度。`nominal_fb` 如保留只作快照，不再当可重复续租的额度。金额均用整数，不能用浮点数。

`work{next_action_height, phase, cursor}` 保留到期阶段和兼容状态，并复用 `rent_expiry_` 定位规范工作键。它不是按 owner 预算把 `due_height <= H` 任务延到下一块的通道：补租回调返回 deferred 视为未完成错误，清户的分页阶段也在当前调用内运行到结束。区块执行失败时整个 StateView 不提交，重放从相同父状态得到相同结果。

在持续收费区间内，设高度 H0 已计提，当前高度 H，可用 FB 为 A，已有欠租为 U：

```text
本次累计应付 D = U + max(H - H0, 0) × 100
本次可支付 P   = min(A, D)
有效可用 FB    = max(A - D, 0)
结算后欠租    = D - P
```

实际结算只做 `用户 FB -= P`、`租金 fund FB += P`，总发行量不变。未收租金是租金状态中的欠款，不能提前给 fund 记成资产。名义总资产、有效可用资产、冻结资产必须分别展示。

结清旧欠租后，仍需收费且有可用 FB 时，经济到期高度为 `H + ceil(availableFB / 100)`；没有可用 FB 或仍有欠租时，立即进入 needs_funding。最后不足 100 的余额只支付实际能付的数额，余下部分记欠租并进入补租，不能凭空补足整块租金。高度加法和整数转换必须检查溢出。

计费区间定义为 **(H0, H]**：在 H0 新激活或从免租降为收费的账户，当块不收费，下一块开始。相同账户同一高度多笔交易不会重复计提，但后续入款仍可再次支付已经记下的欠租。免租期间不增加新租金；进入免租前必须保留并结清历史欠租，不能靠一笔入款抹掉它。转出导致失去免租资格，从该转出的执行高度开始新的收费区间。支付旧欠租后才用新的净名义资产判断免租，不能把本应支付的 FB 同时算成免租资产；外置资产达标但旧欠租仍未付时保留债务及待处理任务。

例如在 20423 收到 0.01 FB（1,000,000 最小单位），持续收费到 30422：

```text
已产生租金 = (30422 - 20423) × 100 = 999,900
有效余额   = 1,000,000 - 999,900 = 100 最小单位 FB
```

所以无法再转走完整的 0.01 FB；100 也不足以单独支付当前 1000 的交易手续费。

## 执行顺序与回滚

用户交易沿用验签、nonce 与手续费规则，增加显式租金屏障：

1. 验证身份和 nonce。nonce 不符时，不因这笔无效交易扣费或推进 nonce。
2. 发送方按当前执行高度结算历史租金；欠租未解除时不得发起新的转出或占资。
3. 保存已结租的快照，再扣 runtime fee，保存扣费快照。
4. 执行业务。接收方、maker 和其它实际受影响账户，在首次资金变化前结算旧区间，再在变化后更新租金资格。
5. 业务失败按原规则回滚业务、保留费用并推进匹配的 nonce；发送方此前已结租不回滚。手续费不足时保留已结租，按现有匹配 nonce 消费规则处理。
6. 块末处理当前高度的到期工作集和其它协议资金事件；在所有 `due_height <= H` 工作清空后，最后在同一 StateView 上做金额守恒审计和持久化。

动态接收方/maker 的结算允许随失败业务一起回滚，前提是余额、计提高度、欠租、到期索引及执行期缓存一起回滚。回滚后数学上的旧租金仍存在，下次触碰继续结算；不引入独立的第二套提交系统。整块失败时所有变动一起丢弃。

租金拒绝属于业务失败时也遵守已匹配 nonce 的消费规则；对应交易可能只收取能够实际支付的历史租金而没有 runtime fee，必须返回明确回执。协议履职交易沿用现有 nonce 豁免和成功退 runtime fee 规则，但不能因此免除账户历史租金。

覆盖范围不能只有 `TransferTxHandler`：

- 转账的发送方与接收方，包括给已有欠租账户入款。
- 下单、maker 被动成交、撤单解冻、增加/减少保证金。
- 充值确认、提现退款、挑战贡献返还、奖励、资金费与强平等协议资金变动。
- 资产 claim 的变化及免租门槛的升降。

逻辑集中在 `rent/` 与 `vm/rent_hooks.go` 的适配层；资金写入入口显式调用同一屏障，不在每个业务 handler 复制算法。maker 结租或补租撤单后，必须重新验证订单和可用量；不能继续执行旧快照。未支付租金不得直接从正在承担风险的保证金/质押中抽走，由既有解冻、清算或 cleaner 迁移真资金。

普通撮合的 maker 若不能用可用 FB 结清欠租，本次跳过并交给块末到期工作集，不在普通撮合内部递归启动换币。若该 maker 在本块产生了 `due_height <= H` 的新工作，必须动态入队并在本块完成。强平、资金费、罚没等既有强制义务不能被租金欠款阻塞：先计提欠租，按原规则完成风险资金变动，再用净可用 FB 支付；不能让收租抢先抽走履约所需的锁仓/保证金，也不能把这种强制变动误当成用户主动新增占资。

资金释放或被动入款允许到账，但先补欠租，只有净剩余可以被后续操作花掉。这样不会把“释放自己的锁仓资金来补租”也一并阻塞。

## 只剩 1 ETH.USDT、没有 FB

复用当前自动兑换能力：仅对白名单资产，按共识确定的交易对、父状态参考价格和滑点上限尝试真实撮合。maker 扫描仍分页限制单次内存和撮合步长，但一个到期 owner 的可用外部资产补租必须在清户前于同块完整执行。1 USDT 不等价于任何固定数额 FB，也不能由协议凭空补出 FB。

实现只兑换“历史欠租 + 0.01 FB 续租余额”所需金额，不默认卖完整个 1 USDT。欠租先支付，净余 FB 再支持后续租期。目标及所有限额是全网一致的协议常量。只花可用外置资产；冻结款由既有撤单/解冻流程释放，不能根据 claim 索引直接增加 fund。

兑换成功额度按本次成交实际净增加的 FB 计算，扣除成交费用，不能直接拿成交事件数量当净到账。自动补租排除账户自己的 maker，避免自成交和已有资金内部搬动被误算成新租金收入。

结果必须区分：

| 结果 | 处理 |
| --- | --- |
| 成交且覆盖欠租 | 实际扣除卖出资产、收到 FB、支付欠租，剩余 FB 续租 |
| 部分成交仍有欠租 | 保存真实成交，重新结算剩余欠租，并在同块继续尝试其它可用资产；确认再无可用流动性后才能清户 |
| 需要继续下一页（含 32 个 maker 步长） | 在补租回调内继续处理；如果满页却没有成交、移除阻塞键或其它可验证进展，则返回区块执行错误，不得跨块 deferred 或误清户 |
| 确认没有合适流动性或价格越界 | 按既有到期清理规则处理，由 cleaner 将真实资产转入回收 fund |
| 数据读取或解码失败 | 返回执行错误，不能伪装成零余额或无流动性 |

自动兑换过程不能递归启动无限层“为 maker 补租再撮合”。对手方只执行直接 FB 结算和资格检查；需要进一步自动换币的对手方本次跳过，其新产生的到期工作由同块工作集处理，本次重新选取可履约挂单。所有重选、跳过和扫描都必须有固定单页上限和可验证进展，分页只限制每次操作量，不限制当块总处理量。

当前无流动性后会清户并归集其它资产；此草案保留该语义。增加宽限期或允许赎回回收资产属于额外产品规则，应单独决定，不能偷偷夹在惰性扣租中改变。

## 到期处理与性能

每块工作量取决于本块实际触碰的账户、当前高度实际到期的账户及其需要清理的状态，与未到期总账户数无关：

```text
主要读取/计算 ≈ O(本块资金事件 + 不同 touched owners + D log D + 到期 owner 的实际补租/清理工作)
当块工作集空间     = O(D + 动态新增到期工作)，持久状态继续复用现有 state / expiry 索引
```

其中 D 是本块实际命中的 `due_height <= H` 工作数。分页大小只控制单次读取、批量预取和内存峰值，不是 owner 总预算，也不能改变最终状态。

顺序索引定位有 O(log N) 的 seek 成本。初始 `rent_expiry_` 工作集在任何租金 hook 写入或删除该前缀前，使用单调 `startAfter` 完整扫描并按完整 `(due_height, owner)` 键排序去重；不允许每处理一个 owner 就从前缀起点重扫。查询使用高度和余额一致的 finalized 快照，按账户点读租金状态、余额及少量白名单聚合。

到期工作集遍历 **due_height <= 当前高度** 的有序索引，按完整 key 的固定顺序处理。本块执行中新产生或改写的 `due_height <= H` 规范工作键显式动态入队，并与已预取页比较完整 key 来保持全局顺序。每个 owner 处理后重新校验当前规范工作键，块末再用一次 `limit=1` 检查确认没有未跟踪的已到期工作；任一检查失败都使区块执行失败，不进入下一高度。

自动兑换、清理和到期 owner 预取都使用固定单页大小；例如单次 maker 扫描仍为 32。这些数值只限制单次扫描、写入和回滚峰值，运行时在同块循环消费后续页，不存在“每块最多 64 owners”的业务语义。单账户拥有大量订单/余额/claim 时，其实际清理成本仍与该账户的真实状态量相关；分页不得隐藏或跨块转移这项工作。

读取先按 owner 汇总去重，再分页批量预取 rent state、FB balance、claim marker 和 owner marker。只有 `OwnerMarkerInit` 存在时，才能把 marker 集合视为完整证明：此时缺少 non-FB balance/claim/spot order/future order marker 可安全跳过对应的外部资产、claim total 或订单读取；旧账户没有 init marker 时必须保守读取，不能把缺 marker 当成零资产。

future funding 不再为每个到期 owner 从头扫描全局 `future_orderstate_`。在完整 owner marker 证明没有 future order 时直接跳过；任一当块 owner 需要扫描时，使用单调游标分页把共识 `future_orderstate_` 在本块最多建立一次 `owner -> open order keys` 分组索引，后续 owner 复用分组结果。该索引只是当块执行期加速结构，不取代 StateDB 真源，也不增加每笔 futures 成交的持久写放大。

清理中账户禁止新占资和转出；资金按页从执行真源移出并等额进入 fund，每页守恒，完成真实迁移后才能删除索引和最终账户状态。入款必须走同一租金状态判断，不能使分页游标之前的资产成为漏网项；建议清理阶段禁止普通转账入款，协议不可拒绝的入款显式加入待清理工作集。

每页源余额扣减与 fund 入账写入同一 StateView，调用内游标只能在该页资金迁移完成后推进；整块最终原子提交，不得先推进游标再异步删除资金来源。

1 亿账户在同一高度到期仍然需要在该块处理 1 亿账户，这是用户要求“到期块必须全部完成”带来的实际最坏成本，不能通过跨块排队消除。当块完成与极端同高度集中到期时的固定出块时间无法同时保证；正常运行要依靠到期高度分布、批量 IO 和避免重复扫描来降低成本。只有用户查询的账户需要投影，不会为了更新界面遍历全库。

同块批量预取后，最终 owner 处理和写入仍按确定性顺序串行，避免并发写 StateView 造成状态根漂移。执行期“已结算”缓存只能在 StateView 内并参与回滚，不能用一个永久 map 跳过后续真实结算。免租资格和余额可在同块多次改变，去重只减少重复计提，不能跳过变化后的状态刷新。

## 查询与钱包接口

保留现有名义字段供兼容，并新增清楚的口径：

- `as_of_height`：本次一致快照对应的 finalized 高度。
- `last_accrued_height`：`rent_state_` 已持久化的计提游标；旧记录缺失时回退到 `last_settled_height`。它不会因为只读查询高度前进而改变。
- `last_settled_height`：最近一次租金状态处理/落盘高度的兼容字段，不代表一定发生正额扣款。
- `nominal_fb`：现有名义资产总额，含锁仓和 claim。
- `available_fb`：账面可用 FB。
- `pending_rent_fb` / `unpaid_rent_fb`：截至 `as_of_height` 的投影应付及已计提未付口径；只读投影不表示已经写账扣款。
- `spendable_fb`：按 `as_of_height` 扣除待结租金后的预计可花 FB；钱包估算可转额还需减 runtime fee。
- `state`：exempt / renting / needs_funding / sweeping；`work` 给出规范到期高度和阶段兼容信息，不表示允许把当前高度已到期的 owner 延到后续区块。

`/account/asset`、Explorer 余额、钱包最大金额、txpool 资金预留共用同一投影规则。txpool 只预检查 finalized 高度和本地已预留支出，不做持久结租或自动换币；交易晚于估算高度执行可能增加租金，最终由 VM 决定并返回明确原因。不得把 frozen/claim 总额展示成可转余额，也不能把缺少租金字段默认为“无需租金”。

## 首次发布与实施顺序

第一版尚未发布，因此直接以本设计作为首次发布规则，不增加新的协议版本和升级高度。已有 `rent_state_` 从记录的 `LastSettledHeight` 继续计费；没有租金状态的账户在首次资金触碰时建立起点，当块不倒扣历史租金。全程不需要在某个区块遍历全库。

账户的经济到期可能早于旧 due 索引，尤其是只有锁仓 FB 的账户。查询和资金屏障按当前租金启用条件直接生效；首次触碰若产生 `due_height <= H` 的规范工作键，必须进入当块工作集完成物理补租或清理。旧 due 不能重置计费起点，也不能在等待时给出免费可花额度。

首次发布前应通过测试数据检查所有应收费账户都能在资金触碰时建立状态，并由 due 索引继续调度。查询索引不作执行依据。

推荐实施顺序：

1. `rent/`：统一投影、租金状态、真实扣租、欠租、守恒测试和启用规则。
2. `vm/`：发送方与所有资金事件的租金屏障、回滚、动态对手方、块末到期处理。
3. `rent/` + VM cleaner：旧 due 补处理、明确 funding 结果、同块分页清理、失败后确定性整块重放。
4. `txpool/`、`handlers/`、Explorer/钱包：统一有效余额、费用预留、余额口径和错误提示。
5. 集成验证：跨块、同块多交易、重放/快照、分页边界和负载；完成后再安排首次发布。

## 验收条件

- 20423 → 30422 示例严格得到 999900 租金；转走原始 0.01 FB 失败，不产生额外余额。
- 空闲 10000 块不产生账户逐块写；查询随高度变化且不写库；触碰一次只结清一次。
- 同块多次转账不重复计费；阈值上穿不能抹旧债，下穿从下一块开始收费。
- nonce 错误、fee 不足、业务失败、业务回滚、整块失败和协议退费边界全部按约定验证。
- 接收方/maker/充值/解冻/资金费/claim 变化不绕过欠租屏障；余额与风险资金不被凭空抽走。
- 1 ETH.USDT+0 FB 覆盖充足流动性、部分成交、无流动性、坏价、跨多个 maker 页和读取错误。
- 超过 10000 个同高度到期账户必须在该块全部完成且不遗漏；第 65 个 owner 和第 33 个 maker 不能因分页边界被延期或误清户。
- 单账户大状态分页每页金额守恒，但同块运行到完成；执行中断、重启或 checkpoint 恢复后从相同父状态重放得到相同结果，不重复收租或归集。
- 多节点同一父状态及相同区块重放得到相同 rent state、余额、due 索引和状态根。
- 负载测试分别改变总账户量、本块活跃量和同高度到期量，证明无每块全账户扫描，并断言到期索引扫描次数、批量读取键数、future order 全局建索引次数、撮合页数与清理页数的复杂度上界。墙钟耗时仅作辅助，本文不声称已部署或已在 local20 实测。
